# make g2: upstream baselines and the H-knee sweep

**What:** measures upstream kraken2 at the pin on RODA v205 (Law 2: upstream at its best), as
the G2 issues ask:
- #21, NVMe baseline: `--memory-mapping` on instance-store NVMe, thread count tuned by sweep,
  cold and warm;
- #22, big-RAM baseline: the default load (no `--memory-mapping`) on a 1536 GiB node, load time
  separate from classify, cold and warm;
- #23, the H-knee thread sweep in three regimes, with each knee candidate's signature captured
  per rung.

Backed by `scripts/g2.sh` (the driver), `scripts/lib/g2run.py` (one instrumented run),
`scripts/lib/g2summary.py` (the summary), `scripts/g2-instance.sh` (instance setup),
`scripts/lib/etagcheck.py`, `scripts/madvrandom-build.sh` and the plans in `scripts/g2/`.

```bash
make g2 PART=local                                   # smoke test on the viral DB (macOS or Linux)
make g2 PART=summary DIR=results/g2/<run>/out/g2-nvme  # rebuild summary.md from runs.jsonl
make run GATE=g2 SPEC=runs/g2-smoke.json             # AWS smoke test: every regime and instrument
make run GATE=g2 SPEC=runs/g2-nvme.json              # #21 + #23 (b)/(c): r8gd.16xlarge
make run GATE=g2 SPEC=runs/g2-ram.json               # #22 + #23 (a): r8gd.48xlarge
make run GATE=g2 SPEC=runs/g2-c8gd.json              # #21 on c8gd (and g2-c9gd.json on c9gd)
make orphans
```

## Regimes

| regime | binary | flags | table |
|---|---|---|---|
| `load` | upstream at the pin | default | read into RAM by upstream's `K2_DB_READ_THREADS` pread streams (default 8) |
| `ram` | upstream at the pin | `--memory-mapping` on a tmpfs copy mounted `huge=always` | resident in RAM (shmem, 2 MiB pages); no per-run load |
| `mmap` | upstream at the pin | `--memory-mapping` on NVMe | page cache over NVMe; faults read the table |
| `madv` | **kraken2-madvrandom** | `--memory-mapping` on NVMe | as `mmap`, with `madvise(MADV_RANDOM)` on the mapping: no fault read-around |

`kraken2-madvrandom` is a diagnostic build only, never the oracle or a baseline.
`scripts/madvrandom-build.sh` exports the pinned tree with `git archive`, applies
`upstream/madvrandom.patch` (four lines in `MMapFile::OpenFile`), and installs into
`.oracle/<pin>-madvrandom/`. Its `BUILD` records the patch sha256. The pristine checkout and
`scripts/oracle-build.sh`'s install are untouched.

The `ram` regime exists so that a 13-rung sweep does not pay 13 loads of 1.19 TB. Part 1 of
`runs/g2-ram.json` runs the same input under `load` at T = 8 and 64, gz and fq, so the two are
compared cell for cell.

## Plans

A plan is a checked-in text file, executed in order:

```
run REGIME INPUT STATE REPS T1 T2 ...   # for rep in 1..REPS: for T in T1 T2 ...: one rung
profile REGIME INPUT STATE T            # one perf record -g run, not counted in any cell
env NAME=VALUE ...                      # classifier env for the following lines (env - clears);
                                        # such cells are labelled e.g. load[K2_DB_READ_THREADS=32]
readahead KB | default                  # host tune: read_ahead_kb of every G2_DEVS device (the mmap
                                        # read-around window); cells are labelled
                                        # e.g. mmap[read_ahead_kb=4]; default restores boot values
note TEXT                               # copied into the manifest
```

**Warm means warm for that input.** Every cold rung drops the page cache. So a warm rung measures
its own input's cached pages only if it directly follows a rung on the same input and regime.
The summary marks other warm cells `warm!`: they are not warm measurements. Plans should put
each warm rung right after its own cold rung. (`runs/g2-nvme2.json` and the c-family runs
did not do this for the per-accession rungs.) The `ram` regime is exempt, because
`drop_caches` does not touch tmpfs.

`INPUT` is `NAME-gz` or `NAME-fq`, for `G2_READS/NAME_{1,2}.fq[.gz]`, paired, or `empty` (a
zero-byte FASTQ: load only). `STATE` is `cold` (the page cache is dropped first: `ak2_drop_caches`
on AWS) or `warm`. Every rung runs with `--output` and `--report`, like a real run.

**Order (Law 4, cheapest first).** In the I/O-bound regimes, the highest thread count is the
cheapest rung, so ladders run from the highest T down. Rep 1 of everything runs before rep 2.
A rung that exceeds `G2_RUNG_TIMEOUT` is killed and recorded as censored. The same plan line's
smaller thread counts are then skipped, because they would be slower. `G2_DEADLINE` skips every
rung not started by then, so there is time left for the summary and the push.

## Workload sizing and resolution

Upstream's classify hands out **8 MiB input blocks** (`INPUT_BLOCK_BYTES` in `classify.cc`; a
block of mate 1 plus as many mate-2 records). With B blocks:
- T threads can have at most min(T, B) busy;
- the makespan is ceil(B/T) block-times, against B/T ideal.

SRR062634's 200k-pair subset is **7 blocks**, so **no rung on it can use more than 7 threads.**
The summary therefore shows B/T and the quantization ceil(B/T)/(B/T) per rung. It flags rungs
with B < 2T as unable to resolve scaling. On those rungs it does not read the
critical-section signature, because idle threads wait at the OpenMP barrier in futex.

| plan | input | pairs | blocks | used for |
|---|---|---|---|---|
| nvme | SRR062634_2000000 | 2 M | 62 | T = 8..64 ladders. T = 48/64 have under 2 blocks per thread; the quantization is shown |
| nvme | SRR062634_250000 | 250 k | 8 | T = 1..8 ladders. At QD 1, a cold 1-thread rung on 2 M pairs would take hours. T = 8 is on both ladders, so the effect of workload size is measured |
| ram | SRR062634_8000000 | 8 M | 247 | T = 1..192 ladders (>= 2 blocks per thread up to T = 123) |
| all | <acc>_200000 | 200 k | 6-9 | the per-accession baseline at one T |

All are prefixes of real public samples. The 8M-pair subset is
`scripts/fetch-reads.sh SRR062634 8000000`, staged with
`STAGE_READS_N=8000000 STAGE_READS_RUNS=SRR062634 make stage-reads`. The instance derives the 2M
and 250k prefixes with `head`, gzips them with `-6 -n`, and writes their sha256 into a `SOURCE`.
Each ladder keeps one workload for every thread count.

## What one rung measures

`g2run.py` times the same way as `lbrun.py`:
- `wall_s` is exec to exit;
- `load_s` is up to `Loading database information... done.`;
- `classify_s` is upstream's own `processed in`.

The **classify window** runs from `done.` to the `processed` line. Over that window it records:

| candidate | signature | instrument |
|---|---|---|
| synchronous faults cap NVMe queue depth | aqu-sz ~ busy threads | `/proc/diskstats` time-in-queue delta / window (iostat's aqu-sz) on the NVMe members; r/s, KiB/IO, MiB/s; md0 too |
| read-around amplification | disk bytes >> 4 KiB x pgmajfault | `/proc/vmstat` pgmajfault delta and disk read bytes |
| critical sections | futex / off-CPU time grows with threads | thread-state sampler (`/proc/PID/task/*/stat` + `syscall`, 20 Hz): R, D, S in futex, S in read; `perf stat` task-clock gives off-CPU = 1 - task-clock / (T x window); `syscalls:sys_enter_futex`, context switches; `profile` lines give hot symbols (libgomp spin vs `Get`) |
| DRAM/TLB limits | dTLB misses, low IPC | `perf stat` cycles, instructions, dTLB-loads, dTLB-load-misses, `dtlb_walk`, `stall_backend` |
| single-stream gzip | read-blocked threads; the knee moves with plain input | the same ladder on `-gz` and `-fq`; the sampler's state of the wrapper's `gzip -dc` children (R = busy) and threads in `read`; `g2i_gzip_rate` logs one gzip stream's rate on the box |

`perf stat` starts disabled (`-D -1 --control fifo:`) as the classifier's parent. It is enabled at
`done.` and disabled at `processed`, so load-phase counts never mix in. Setup sets
`kernel.perf_event_paranoid=-1`, and probes each event on the box (`G2_PERF_EVENTS` lists the ones
that work).

**Could the probe resolve it?** The summary answers this per ladder and candidate:
- queue depth needs >= 1000 read IOs in the window;
- read-around needs >= 1000 major faults;
- critical sections needs >= 50 samples at >= 2 thread counts with >= 2 blocks per thread;
- DRAM/TLB needs the perf counters;
- gzip needs the same cell in both formats.

A ladder step counts as resolved only when the two rungs' min-max ranges are separated. The knee
is the first step with efficiency below 0.5, where efficiency = (gain - 1) / (thread ratio - 1).

## On AWS

| spec | box | why |
|---|---|---|
| `g2-smoke` | r8gd.xlarge | every regime and instrument once, on Standard-8 (minutes, cents) |
| `g2-nvme` | r8gd.16xlarge: 64 vCPU, 512 GiB, 2 x 1900 GB NVMe (RAID0) | r8gd (#21) with >= 64 vCPUs for the 1-64 sweep. Of the >= 64-vCPU r8gd sizes it has the least RAM that can still cache the 2M-pair working set |
| `g2-ram` | r8gd.48xlarge: 192 vCPU, 1536 GiB, 6 x 1900 GB NVMe (RAID0) | the >= 1.5 TB node with local NVMe for the cold load (x8g.24xlarge has no instance store, and a tmpfs copy plus the default load's anonymous copy would need 2.2 TB) |
| `g2-nvme2` | r8gd.16xlarge (as `g2-nvme`) | the follow-up: the `read_ahead_kb` host tune for the pristine `-M` baseline, the per-accession baseline, profiles, rep 2 of the madv ladders |
| `g2-c8gd` / `g2-c9gd` | c8gd.8xlarge / c9gd.8xlarge: 32 vCPU, 64 GiB, 1 x 1900 GB | the cheapest c8gd/c9gd sizes with >= 1.2 TB NVMe (#21) |

The bodies:
- clone the launch commit;
- source `scripts/g2-instance.sh`;
- RAID0 every instance-store NVMe device (mdadm, chunk 512K, xfs, `/mnt/nvme`);
- stage the reads and check each against its sha256 metadata and `SOURCE`;
- stage RODA v205 with the AWS CLI's CRT client. Each file is checked against the object's
  ETag by recomputing the multipart ETag (`etagcheck.py`: parallel md5 per part, which also
  measures the array's sequential read rate). The upstream builds run during the stage;
- source `scripts/g2.sh` with the plan.

`runs.jsonl` is pushed after every rung. Each `g2.sh` invocation writes `out/g2-<label>/`:
`manifest.json`, `runs.jsonl`, `inputs.json`, `summary.md`, `summary.tsv`, `signatures.tsv`,
`plan.txt` and `detail.tgz` (stderr, perf csv, profiles). The run manifest has the instance
type, price, AZ and cost. `g2-<label>/manifest.json` has the storage string, the THP mode, the
host, the pin identity and the madvrandom build. `log/run.log` has `lscpu`, NUMA, disks,
read-ahead, the stage and ETag rates, and the gzip rate.

## Failure looks like

- `g2: input X: ... missing`: the plan names an input the body did not stage or derive.
- `g2: <tag> timed out after Ns: smaller thread counts ... are skipped`: a censored rung. The
  summary lists the skipped rungs with the reason.
- `ERROR: <file> does not match ETag`: the staged database is not the RODA object; nothing ran.
- Exit 95: `drop_caches` failed, so the cold rung was not run.
- `aws: [ERROR]: invalid literal for int()`: the CRT `target_bandwidth` must be an integer with a
  unit (`25Gb/s`).
